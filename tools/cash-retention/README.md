# Cash Audit retention candidate

Apply the SQL migration, then gateway and UI, to a development deployment first. Configure one trusted always-on Linux worker away from the camera. Install requirements.txt in /opt/daybook-retention/venv and worker.py in /opt/daybook-retention. Use a root-owned 0600 /etc/daybook-retention.env with RETENTION_DSN (TLS-verifying database connection), SUPABASE_PROJECT_REF and RETENTION_STORAGE_KEY for the same project. Use a dedicated restricted database role with access to the policy, manifest, audit and cash_events records and permission to update evidence paths and delete expired events. Protect Storage service credentials as administrative secrets. Install the supplied systemd service and timer; enable the timer only after a synthetic hosted acceptance run. Check systemctl list-timers and journalctl -u cash-retention.service. Event errors are recorded in cash_retention.audit, reported via nonzero exit and retried on the next run.

The singleton cash_retention.policy configures days from receipt to archival, calendar years from archive creation to expiry, calendar years from receipt to metadata expiry, and WebP quality. A hold suspends all phases while active. A hold cannot recover an original already deleted. Before the tool is allowed to remove source files, test actual Storage download, PUT, retrieval, deletion and signed Daybook viewing together. Audit logs contain IDs and actions, no images or tokens. Cloud retention does not implement Jetson SSD cleanup, backup expiry, or orphan reconciliation. Keep camera upload disabled until deployment and site privacy sign-off. Explicitly account for uploaded-but-unconfirmed objects and expired backups before claiming universal disposal.
